# AI Usage Log

## How I used AI on this project
I used AI (Claude Code) as a design-and-pair-programming partner, working one small segment at a
time. For each segment the AI first explained *what* it would build and *how it would work*; I read
that explanation, questioned or adjusted it, and approved it before any code was written. The
design decisions — the stack, the two feature domains, how they stay decoupled, the auth approach,
what to leave out — were mine, made as we went. After building, I ran and tested each segment
myself and only then committed it. Disclosure is grade-neutral; the point of this log is to show
that I understand and can explain every line I shipped.

One row per meaningful AI interaction. The last column is my own explanation, in my own words.

| 2026-10-05 · scaffold | Claude Code | Design a LineLeap-style passes app for this assignment, then scaffold a Flask + SQLite skeleton with a health check and environment-based configuration; explain each file before writing it | Accepted after step-by-step review | I reviewed and approved each file as it was explained | The app starts with `python app.py`. `create_app()` in `app.py` builds the Flask app and calls `db.init_db()` so the database is ready before any request. `config.py` reads `PORT` (default 8000) and `DATA_DIR` (default `./data`) from the environment, so I reconfigure the app by setting env vars, never by editing code. `db.get_connection()` opens the SQLite file at `<DATA_DIR>/lineskip.db` (creating the folder if needed), sets `row_factory` so I can read columns by name like `row["email"]`, and turns on foreign keys. `init_db()` reads `schema.sql` and runs it with `executescript`; because every table uses `CREATE TABLE IF NOT EXISTS`, running it on every startup is safe. | 2026-10-05 · auth | Claude Code | Add session-token authentication: a Flask-free auth service (register, login, verify_session) plus register/login/me routes and a require_auth decorator; explain the security model first | Accepted after step-by-step review | Decided to keep `auth/service.py` free of Flask imports (so the logic is a pure, testable unit) and put the `require_auth` decorator in `app.py` since it is framework glue — I confirmed this split before building | Passwords are never stored in plaintext: `register` runs the password through `generate_password_hash` (salted hash) and only the hash goes in the `users` table; `login` checks the attempt with `check_password_hash`. A successful login calls `_create_session`, which makes a random `secrets.token_urlsafe(32)` token and stores it in `sessions` with an `expires_at` 7 days out. The client sends that token back as `Authorization: Bearer <token>`; `require_auth` pulls it from the header, calls `verify_session`, and either puts the `user_id` on Flask's `g` for the route to use or returns 401. `verify_session` returns the user id only if the token exists and hasn't expired, deleting it if it has. The routes are thin wrappers that call the service and turn an `AuthError` into a 400/401. |
| 2026-10-05 · auth-tests | Claude Code | Add edge-case unit tests for the auth service: invalid/duplicate email, short/wrong password, unknown login, and expired-token purge | Accepted after step-by-step review | I chose to simulate expiry by backdating `expires_at` in the DB rather than waiting, so the expiry branch is tested instantly | Each test drives one failure path in `auth/service.py`: the email and password checks in `register`, the duplicate-email check (the `DUP@` test proves lowercasing blocks case-variant duplicates), the wrong-password and unknown-email paths in `login` (both go through the same `AuthError`), and the expiry branch in `verify_session`. The expired-token test sets `expires_at` to one second ago using `auth._now()`, then asserts `verify_session` returns `None` and that the stale session row was deleted. Together these bring `auth/service.py` to 100% line coverage. |
| 2026-10-06 · passes-schema | Claude Code | Add the Passes data model (venues, pass_products, purchases), a repository SQL layer, startup seeding of Madrid venues, and two read routes; decide the schema shape first (ADR-3) | Accepted after step-by-step review | I decided money is stored as integer cents (not floats), inventory is a `quantity_total`/`quantity_sold` pair, and the future analytics `events` table will have no FK into these tables so the domains stay independent | `schema.sql` now has three Passes tables. `pass_products` tracks stock with two counters so the oversell guard (next segment) is just `quantity_sold >= quantity_total`. `purchases` carries a `status` enum, a unique `redemption_code`, and a denormalized `venue_id` so a purchase can be reported/recorded without joining back through `pass_products`. `passes/repository.py` holds only SQL: `list_venues`/`get_venue`/`list_pass_products`/`get_pass_product` for reads, and `seed_venues`, which inserts sample Madrid venues + pass products only when the `venues` table is empty — so it is safe to run on every startup. `create_app` calls `seed_venues` after `init_db`, and `GET /venues` and `GET /venues/<id>/passes` return the rows as JSON. |
| 2026-10-06 · passes-purchase | Claude Code | Implement purchase() with a race-safe oversell guard, a unique redemption code, a POST /passes/purchase route, and tests | Accepted after step-by-step review | I chose an atomic conditional UPDATE for the stock check instead of read-then-write, so concurrent buyers can't both grab the last unit | `purchase()` first loads the pass product (missing → `PassError`). It then calls `repository.try_claim_unit`, which runs a single `UPDATE ... SET quantity_sold = quantity_sold + 1 WHERE id = ? AND quantity_sold < quantity_total`; if that changes 0 rows the pass is sold out and I raise `PassError("sold out")`. Because the check and increment happen in one SQL statement, the database enforces the limit even under simultaneous requests. On success it makes a unique `redemption_code` (`secrets.token_hex(4)`, uppercased), inserts the `purchases` row as `active` with the price copied from the product and the venue denormalized, commits, and returns the purchase. The route is behind `require_auth`, so the buyer is `g.user_id`. Tests cover the happy path (stock 0→1), sold-out rejection (stock never exceeds total), an unknown product, and that codes are unique across purchases. |
| 2026-10-06 · redeem-refund | Claude Code | Add redeem() and refund() to complete the pass lifecycle, with routes and tests; treat status as a state machine | Accepted after step-by-step review | I added an ownership check to refund (you can only refund your own pass) and routed every status change through a single `set_status` writer | A purchase's `status` is a small state machine: only `active` passes can change. `redeem(code)` looks the pass up by its `redemption_code`; if it is missing or not `active` it raises `PassError`, which is what makes redemption one-time — a second scan of the same code sees `redeemed` and is rejected. On success it sets status to `redeemed` and stamps `redeemed_at`. `refund(purchase_id, user_id)` loads the purchase, rejects it if it is missing, not owned by the caller, or not `active`, then sets status to `refunded` and calls `release_unit`, which decrements `quantity_sold` so the freed spot can be sold again. The `/passes/redeem` route is open because the code itself is the credential (door staff); `/passes/<id>/refund` and `/passes/mine` are behind `require_auth`. Tests cover redeem success, double-redeem rejection, unknown code, refund restoring stock, refund of another user's pass, refund of an unknown purchase, and refund of an already-redeemed pass — bringing `passes/service.py` to 100%. |
